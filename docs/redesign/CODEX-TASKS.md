# Задание для Codex

Перед началом прочитать раздел «Решения владельца: не нарушать» в `README.md`.

Порядок работы: сначала **этап 0** (проверка фактов) и **этап 1** (собрать материалы), потом **этап 2** (реализовать редизайн по `docs/redesign/README.md`), в конце **этап 3** (отчёт). Этапы 1 и 2 можно вести параллельно, но в финальной версии кейсов должны быть реальные материалы, а не кадрирование обложки.

Перед началом прочитать `AGENTS.md`, `docs/redesign/README.md` и открыть в браузере `docs/redesign/prototype.html` и `docs/redesign/case-prototype.html`.

## Этап 0. Проверка фактов

Прежде чем переносить тексты кейсов в новый макет, сверить каждое техническое утверждение в `src/lib/projects.ts` и в таблице «План по всем кейсам» (`README.md`) с исходным кодом и работающей версией проекта. Неподтверждённое — убрать или переформулировать, в отчёте перечислить, что изменено.

Особенно для **ChessRise**:

- Что известно: в Supabase-проекте `chessrise-demo` у всех пяти таблиц `public` (`trainers`, `lesson_packages`, `legal_documents`, `reviews`, `lead_requests`) включён RLS, edge-функций нет. Но это демо-проект, а в стеке указаны Nginx и systemd.
- Выяснить: production работает на Supabase или на своём PostgreSQL? Где реализованы Telegram-уведомление и PDF, и работают ли они в production? Какая схема заявки на самом деле (форма → серверная проверка → запись → Telegram → PDF)?
- Подпись «Основа: Next.js · Supabase» и схему «Путь одной заявки» поправить по результату.

То же сделать для цифр на главной: 488 страниц, 41 тест, «3 проекта в production».

## Этап 1. Материалы для кейсов

Сейчас у каждого проекта только одна обложка (`public/cases/*.webp`), и на обложке ChessRise видна cookie-плашка. Нужно добыть материалы самостоятельно и разложить их по местам. Если что-то добыть невозможно, не выдумывать, а записать в отчёт, что именно нужно от владельца.

### Общие правила

- Скриншоты: viewport **1440×900**, `deviceScaleFactor: 2`, итоговый формат **WebP** (качество ~82, конвертация через `sharp`, он уже есть в зависимостях). Мобильные кадры: **390×844**, DPR 3.
- Перед съёмкой закрыть cookie-баннеры, попапы, чаты поддержки и дождаться загрузки шрифтов и картинок (`document.fonts.ready`, `networkidle`).
- **Никаких реальных персональных и рабочих данных.** Внутренние инструменты (отчётность, учёт ИТ-инфраструктуры) снимать только в демо-версиях с синтетическими данными. Никаких внутренних IP, имён сотрудников, серверов и путей. Правила из `src/lib/public-content.test.ts` распространяются и на картинки.
- Короткие ролики (по желанию, но очень желательно): 6–12 секунд, один ключевой сценарий, запись через Playwright `recordVideo`. Сохранить `webm` и `mp4` (H.264). Без звука. Размер каждого до 3 МБ.
- Скрипт съёмки положить в репозиторий: `scripts/capture-cases.mjs` (Playwright; адреса, состояния и имена файлов вынести в конфиг в начале файла), чтобы материалы можно было переснять одной командой. Добавить npm-скрипт `capture:cases`.

### Куда класть

```
public/cases/<slug>/
  cover.webp          # главный кадр для карточек и стены на главной (заменяет public/cases/<slug>.webp)
  shot-1.webp …       # кадры для блока «Крупно» и галереи
  mobile-1.webp       # мобильное состояние, если есть смысл
  flow.webm / flow.mp4  # короткий ролик главного сценария (если снят)
```

`slug` — как в `src/lib/projects.ts`: `chessrise`, `lunafantasy`, `revalib`, `pioner`, `worktime-reporting`, `infrastructure-inventory`. Старые `public/cases/*.webp` удалить после перехода, пути в `projects.ts` сделать локальными (`/cases/<slug>/…`), `remotePatterns` для `raw.githubusercontent.com` в `next.config.ts` убрать, если он больше не нужен.

Каждый кадр прописать в `projects.ts` (поля `cover`, `closeups` и при необходимости `gallery` — см. «Расширение данных» в `README.md`) с осмысленным `alt` на русском.

## Этап 2. Реализация

Всё по `docs/redesign/README.md`: главная, страницы кейсов, остальные страницы, критерии готовности. Там, где материалы из этапа 1 уже есть, использовать их; где нет — временное кадрирование обложки, как в `case-prototype.html`.

Работать в отдельной ветке; коммиты небольшие и осмысленные. Перед каждым коммитом — `npm run lint` и `npm run typecheck`, перед завершением — `npm run verify` и `npm run test:e2e`.
